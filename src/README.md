# Процедурная программа КТ2

Калинин Лев Алексеевич, ИКБО-31-24. Программа проверяет частотный отклик изделий одной партии и сохраняет протокол.

## Запуск

Язык: Python 3.11. Программа проверена на Python 3.14.7. Совместимость синтаксиса с 3.11 проверена отдельно; запуск на самом Python 3.11 пока не проверен.

Из корня проекта или распакованного архива:

```bash
python3 src/main.py
python3 src/checks.py
```

Свои данные и путь результата:

```bash
python3 src/main.py src/examples/batch.json result.json
```

Из папки src можно выполнить `python3 main.py examples/batch.json result.json`.

## Входные данные

Полный пример находится в `examples/batch.json`. В нем девять списков, соответствующих сущностям ER-модели: product_models, lots, products, employees, recipes, parameters, recipe_limits, test_runs, measurements. Связи задаются идентификаторами. Сначала все данные проверяются, затем выполняется расчет.

Пример записи измерения:

```json
{"run_id": "T1", "point_no": 1, "frequency_hz": 150, "acceleration_m_s2": 1}
```

Это учебные, заранее заданные значения, а не результат замера оборудования. Все точки одного прохода должны быть получены при одинаковых условиях возбуждения и крепления. Используется равномерная возрастающая сетка частот без повторов. point_no задает порядок точек. window_size — положительная нечетная ширина окна сглаживания; после сглаживания нужны хотя бы три точки. Статус входной проверки — NEW. started_at задается в ISO 8601 с часовым поясом. Один запуск обрабатывает проверки одной партии. Повторные проверки одного изделия допустимы. Сводка отдельно показывает все проверки и последние результаты каждого изделия.

## Что считает программа

1. `analyze_response` вычисляет скользящее среднее по полным окнам. Частота каждого среднего — частота центральной точки окна. Затем выбирается один положительный максимум и проверяется допуск. Интерполяции между частотами нет. При плато или максимуме на краю сглаженной характеристики возвращается REVIEW: нужен новый замер. PASS означает соответствие только допуску частоты, FAIL — выход за этот допуск. Это не полное заключение о годности модуля.
2. `summarize_batch` сначала сортирует проверки по product_id, времени начала и run_id. Время сравнивается с учетом часовых поясов. После сортировки один проход считает все статусы и последние проверки каждого изделия. Если время совпало, последней считается запись с лексикографически большим run_id. Номер запуска нужен только для однозначного выбора при равном времени. Для пустой партии оба процента равны null.
3. `save_protocol` сохраняет JSON. Входной файл не перезаписывается. Протокол заменяется после полной записи временного файла в той же папке.

Размер окна и допуск являются условиями учебной методики. Перед применением на реальном стенде метролог должен проверить, не смещает ли сглаживание максимум. При окне 1 сглаживания нет. Программа не оценивает неопределенность измерения и не заменяет поверку/калибровку измерительного канала.

## Ожидаемый результат примера

```text
DEMO-001: PASS; частота: 170
DEMO-002: FAIL; частота: 190
DEMO-003: REVIEW; частота: None
Всего: 3; годных: 1; не годных: 1; на повторную проверку: 1
Уникальных изделий: 3; повторных проверок: 0
Последние проверки: PASS=1; FAIL=1; REVIEW=1
Протокол сохранен: result.json
```

Доля PASS в JSON — 33.333333333333336 %. Поля unique_products и repeated_checks показывают число разных изделий и число дополнительных проверок. Поля final_passed, final_failed, final_review и final_pass_percent относятся только к последней проверке каждого изделия.

Для проверки повторного контроля:

```bash
python3 src/main.py src/examples/repeated_batch.json repeated_result.json
```

В этом примере четыре проверки трех изделий. DEMO-002 сначала получает FAIL, затем PASS. По всем проверкам: PASS=2, FAIL=1, REVIEW=1, доля PASS — 50 %. По последним проверкам: PASS=2, FAIL=0, REVIEW=1, доля PASS — 66.66666666666667 %. Дополнительная проверка одна. Ожидаемый файл — examples/repeated_expected.json. Порядок исходных записей измерений можно менять: программа упорядочивает их по point_no. Неправильный JSON, потерянная ссылка, повтор ключа, отрицательное ускорение, нечисловое значение или нарушенная сетка дают сообщение об ошибке и код завершения 1. Старый result.json при ошибке сохраняется: он относится к прошлому успешному запуску, смотрите вывод терминала. Успешная обработка дает код 0 даже при FAIL или REVIEW.

## Файлы

- `main.py` — загрузка и проверка связей, обработка партии, запись протокола, запуск.
- `analysis.py` — два алгоритма и проверка частотной сетки.
- `checks.py` — проверки расчетов, границ допуска и ошибок входа.
- `examples/batch.json` — воспроизводимый учебный пример.
- `examples/expected_result.json` — ожидаемый JSON для этого примера.
- `examples/repeated_batch.json` и `examples/repeated_expected.json` — повторный контроль изделия и ожидаемый результат.

Сложность расчета с окном: O((n−w+1)·w+n), верхняя граница O(n·w), память O(n). n — число частот, w — ширина окна. Если w может расти до порядка n, худший случай по n — O(n²); при постоянном w=3 расчет линейный. Выбран прямой расчет сумм, чтобы показать вложенный цикл. Скользящая обновляемая сумма могла бы сократить время до O(n), но в этой версии не реализована. Сводка по k проверкам включает сортировку O(k log k) и один проход O(k). Итоговая оценка — O(k log k), дополнительная память — O(k) для отсортированного списка. Длина идентификаторов и строк времени предполагается ограниченной. Подготовка входа выполняется отдельно: сортировка точек каждой проверки требует O(n log n) в худшем случае и учитывается при оценке всей программы.
