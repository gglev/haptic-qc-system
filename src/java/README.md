# ООП-версия на Java

Калинин Лев Алексеевич, ИКБО-31-24. Программа обрабатывает готовые измерения одной партии. Она выполняет те же расчеты, что и исправленная Python-версия КТ2: проверяет данные, оценивает частотный отклик, учитывает повторные проверки и сохраняет JSON.

## Сборка и запуск

Нужен JDK 21 или новее. Сборка выполняется через javac с параметром --release 21. Проверено на Azul Zulu JDK 21.0.12.1. Maven и база данных не нужны.

Для чтения и записи JSON используется [Gson 2.15.0](https://github.com/google/gson/releases/tag/gson-parent-2.15.0). При первой сборке build.sh скачивает библиотеку из Maven Central и проверяет SHA-256. Для скачивания нужны интернет, curl и shasum. JAR и скомпилированные классы не добавляются в Git.

Если curl не может скачать библиотеку из-за сетевой ошибки, можно [скачать тот же JAR в браузере](https://repo.maven.apache.org/maven2/com/google/code/gson/gson/2.15.0/gson-2.15.0.jar) и сохранить как src/java/lib/gson-2.15.0.jar. Затем запустить build.sh. Скрипт проверит SHA-256 и соберет программу без повторного скачивания.

Из корня репозитория:

```bash
cd src/java
java -version
javac -version
sh build.sh
sh run.sh
```

Программа сохранит результат в result.json. После изменения исходников нужно снова выполнить `sh build.sh`. Скрипт очищает только каталог build/classes и собирает программу вместе с тестами.

Свои данные:

```bash
sh run.sh examples/repeated_batch.json repeated_result.json
```

Пути входа и выхода в run.sh отсчитываются от src/java. Для файлов в других папках можно передать абсолютные пути.

Если в системе несколько JDK, можно указать нужный на один запуск. Например, для установленного Zulu на macOS:

```bash
JAVA_HOME=/Library/Java/JavaVirtualMachines/zulu-21.jdk/Contents/Home sh build.sh
JAVA_HOME=/Library/Java/JavaVirtualMachines/zulu-21.jdk/Contents/Home sh run.sh
```

Для Windows PowerShell из src/java:

```powershell
New-Item -ItemType Directory -Force lib, build/classes | Out-Null
curl.exe -fL https://repo.maven.apache.org/maven2/com/google/code/gson/gson/2.15.0/gson-2.15.0.jar -o lib/gson-2.15.0.jar
Get-FileHash lib/gson-2.15.0.jar -Algorithm SHA256
$sources = Get-ChildItem -Recurse src, tests -Filter *.java | Select-Object -ExpandProperty FullName
javac --release 21 -encoding UTF-8 -cp lib/gson-2.15.0.jar -d build/classes $sources
java -cp "build/classes;lib/gson-2.15.0.jar" qc.app.Main examples/batch.json result.json
java -cp "build/classes;lib/gson-2.15.0.jar" qc.Checks
```

SHA-256 библиотеки: `96d3dd843dc2911de01cdabcd50064cb9e860353102a0a78c96fd833d396fc7d`. Команды PowerShell приведены для запуска на Windows; проверка программы выполнялась на macOS.

## Вход и результат

Файлы examples/batch.json и examples/repeated_batch.json скопированы из Python-версии без изменения данных. Вход содержит девять списков: product_models, lots, products, employees, recipes, parameters, recipe_limits, test_runs и measurements.

Пример точки:

```json
{"run_id": "T1", "point_no": 1, "frequency_hz": 150, "acceleration_m_s2": 1}
```

Номер точки — положительное целое число. Частота задается в Гц, ускорение — в м/с². Точки упорядочиваются по point_no. Нужна возрастающая равномерная сетка частот. window_size — положительное нечетное число, после сглаживания должно остаться хотя бы три точки. started_at задается в ISO 8601 с часовым поясом, например `2026-11-19T10:00:00+03:00` или `2026-11-19T07:00:00Z`. В расчетах времени сохраняется точность до микросекунд, как у Python datetime. Проверки на входе имеют статус NEW.

Вывод первого примера:

```text
DEMO-001: PASS; частота: 170.0
DEMO-002: FAIL; частота: 190.0
DEMO-003: REVIEW; частота: null
Всего: 3; годных: 1; не годных: 1; на повторную проверку: 1
Уникальных изделий: 3; повторных проверок: 0
Последние проверки: PASS=1; FAIL=1; REVIEW=1
Протокол сохранен: result.json
```

В повторном примере четыре проверки трех изделий. DEMO-002 сначала получает FAIL, затем PASS. Среди всех проверок PASS=2, FAIL=1, REVIEW=1, доля PASS равна 50 %. Среди последних проверок изделий PASS=2, FAIL=0, REVIEW=1, доля PASS равна 66.66666666666667 %.

Последняя проверка выбирается по времени с учетом часового пояса. При равном времени используется лексикографически больший run_id. Первые неудачные проверки сохраняются в общей статистике. Для пустого списка оба процента равны null. Ожидаемые результаты лежат рядом с примерами в expected_result.json и repeated_expected.json. Содержимое JSON сравнивается по значениям; запись числа 170.0 вместо 170 не меняет результат.

Данные учебные. PASS означает соответствие только допуску частоты максимального отклика. Управление стендом, запись EEPROM, подключение PostgreSQL и обмен с MES/ERP на этом этапе не реализованы.

## Классы и пакеты

- qc.model — девять сущностей ER-модели, метролог, интерфейс анализатора, результат расчета и общие правила проверки данных.
- qc.analysis — два анализатора и сводка партии.
- qc.app — загрузка JSON, хранение набора объектов, запуск обработки и запись результата.
- tests/qc/Checks.java — проверки программы без отдельного тестового фреймворка.

Employee.canApproveRecipe возвращает false. Metrolog наследует Employee и переопределяет этот метод, возвращая true. Конструктор Recipe вызывает метод через ссылку Employee и не разрешает обычному оператору утверждать методику. Чтобы сохранить формат JSON КТ2, загрузчик создает Metrolog для сотрудников, на которых ссылается approved_by. Это учебная модель роли, а не авторизация пользователя в системе.

ResponseAnalyzer имеет две используемые реализации. RawResponseAnalyzer работает при окне 1. MovingAverageAnalyzer применяет вложенный цикл сглаживания при большем окне. Загрузчик выбирает анализатор и передает его в Recipe через интерфейс. Методика проверяет, что размер окна анализатора совпадает с ее настройкой. Общие проверки и поиск максимума вынесены в ResponseRules и AnalysisResult.

Объекты связаны ссылками: Product хранит Lot, TestRun хранит Product, Recipe и Employee. RecipeLimit связывает Recipe и Parameter. TestRun создается после проверки входных данных и содержит свой неизменяемый список точек. Поэтому в UML у связи с Measurement указана композиция и минимум три точки. Результат до расчета отсутствует, затем сохраняется в AnalysisResult.

Коллекции List хранят точки и проверки, Map — записи по идентификаторам и счетчики, Set — занятые ключи и номера точек. Все поля закрыты. Списки точек снаружи нельзя изменять через геттер.

В папке models от корня репозитория в classes.puml находится один исходник четырех схем. classes.png показывает пакеты, classes_model.png — данные и общие правила, classes_analysis.png — анализаторы, classes_app.png — загрузку и запуск. На подробных схемах показаны поля и открытые методы с типами. Конструкторы и закрытые вспомогательные методы опущены. Обозначение external указывает на класс, подробно показанный на другой схеме.

## Ошибки и сохранение

Успешная обработка завершается с кодом 0 даже при FAIL или REVIEW. Ошибка входа, чтения или сохранения дает код 1. Входной файл не перезаписывается. Все данные проверяются до расчета. Протокол сначала записывается во временный файл в той же папке, затем атомарно заменяет предыдущий. Если файловая система не поддерживает атомарную замену, программа сообщает об ошибке. При неудачном запуске старый протокол относится к предыдущему расчету.

## Проверки

Из src/java после сборки:

```bash
java -cp 'build/classes:lib/gson-2.15.0.jar' qc.Checks
```

Проверяются оба файла с ожидаемыми результатами, два анализатора, поведение метролога, порядок точек, повторный контроль, одинаковое время, разные часовые пояса, пустая партия, потерянные ссылки, дубликаты и неверные значения. Отдельно проверяется сохранность входа и старого результата после ошибки.

Из корня репозитория можно сравнить версии:

```bash
python3 tools/compare_versions.py
```

Проверка использует Python-версию из src/main.py и собранную Java-версию. На одинаковых данных сравниваются полные JSON, коды завершения и сохранность старого результата при ошибке. В набор входят 100 случаев, в том числе 60 наборов с фиксированным начальным значением генератора случайных чисел. Python нужен для этого сравнения, запуск Java-программы от него не зависит.

## Сложность

Для n точек и окна w сглаживание занимает O((n−w+1)·w+n) времени и O(n) дополнительной памяти. При w=1 обработка линейная. В BatchSummary k проверок сортируются за O(k log k), затем просматриваются один раз. Дополнительная память сводки — O(k). Длина идентификаторов и строк времени считается ограниченной. Эти оценки совпадают с исправленной процедурной версией. Сортировка исходных точек по point_no учитывается отдельно: O(n log n) на одну проверку.
