# Модели для КТ2

В КТ1 выбран процесс выходного контроля и настройки тактильных модулей. Здесь описана целевая система и отдельно алгоритмы учебного прототипа.

## Файлы

- `models/process.puml` — код изображения процесса для PlantUML.
- `models/process.bpmn` — модель BPMN 2.0 с дорожками и координатами элементов.
- `models/data_model.puml` — логическая модель данных в нотации Crow's Foot.
- `models/algorithm_1.puml` — проверка таблицы с вложенными циклами.
- `models/algorithm_2.puml` — поиск максимума и проверка частоты.
- Одноименные PNG — изображения диаграмм для просмотра без расширений.

В `process.puml` и блок-схемах используется DOT внутри PlantUML (`@startdot`). Это позволяет явно задать круги событий, ромбы и параллелограммы. Поддержка DOT описана в [документации PlantUML](https://plantuml.com/dot). Файл `.puml` служит кодом изображения; для открытия в BPMN-редакторе нужен `process.bpmn`.

## Бизнес-процесс

В модели четыре дорожки: ОТК, ПО, Метролог и MES/ERP. Начало — поступление изделия на контроль. Метролог утверждает методику и версию допусков. MES выдает задание, после чего оператор ОТК сканирует номер и устанавливает изделие.

ПО проверяет готовность стенда, получает измерения и проверяет их пригодность. Если стенд или данные не подходят, метролог выясняет причину и разрешает новый запуск. Ошибка измерений не считается доказанным браком изделия.

Шлюз качества разделяет изделия по результату сравнения с допусками. Для годных модулей предусмотрены настройка и проверка записи параметров. Для остальных оформляется несоответствие. Ошибка записи блокирует выпуск и сохраняется отдельно от брака изделия.

После сохранения протокола ПО передает его в MES. При повторной отправке номер протокола используется для защиты от дубликатов. До подтверждения приема выпуск ожидает синхронизации. Время ожидания в модели — пример настройки повторной отправки, оно не задает время контроля изделия. MES и ERP объединены в дорожку для учебной модели: MES хранит производственный результат, ERP использует его для учета партии.

Подключение стенда, запись в устройство и обмен с MES — части целевого процесса. Текущий Python-прототип работает только с готовой таблицей и JSON, поэтому не выполняет весь BPMN-процесс.

## Логическая модель данных

В модели девять сущностей: модель изделия, партия, изделие, сотрудник, версия методики, контролируемый параметр, допуск параметра, проверка изделия и точка измерения.

Основная цепочка: модель изделия → партия → изделие → проверка → точки измерения. Одно изделие можно проверять несколько раз. Каждый запуск хранится отдельно и ссылается на примененную версию методики. Проверка с ошибкой может не иметь ни одной точки измерения, поэтому связь с Measurement допускает ноль записей.

Связь «многие-ко-многим» находится между Recipe и Parameter. Одна методика задает допуски нескольких параметров, а один параметр используется в нескольких методиках. Связующая таблица RecipeLimit хранит границы для пары `(recipe_id, parameter_id)`. Например, параметры могут иметь коды `peak_frequency` и `peak_acceleration`. Пока программа проверяет только частоту.

В диаграмме PK — первичный ключ, FK — внешний ключ, UQ — уникальное значение. Звездочка отмечает обязательный атрибут. Обозначения связей взяты из [документации PlantUML по Information Engineering](https://plantuml.com/ie-diagram).

### Почему модель соответствует 3НФ

1. Каждое поле хранит одно значение. Точки измерения находятся в отдельных строках, а не в списке внутри изделия.
2. В RecipeLimit границы зависят от всей пары ключей. Нельзя определить допуск только по параметру: в разных версиях методики он может различаться. В Measurement частота и ускорение зависят от пары `(run_id, point_no)`.
3. Название модели, имя сотрудника и единицы параметра хранятся в своих сущностях. Они не копируются в TestRun и RecipeLimit. В Product хранится ссылка на партию, а модель определяется через Lot и не дублируется.

Для модели приняты правила: номер партии и серийный номер изделия уникальны во всей системе; все изделия одной партии относятся к одной модели; единица параметра едина; один проход не содержит повторных частот. Если эти правила изменятся, модель нужно пересмотреть.

Утвержденная методика не редактируется: изменение допусков создает новую версию. `approved_by` ссылается на сотрудника, который утвердил методику; `operator_id` — на оператора конкретного запуска. Статус TestRun хранит принятое решение на момент контроля, включая ошибки; это не изменяемый текущий статус самого изделия.

Нужно проверять, что методика относится к той же модели, что изделие, что lower_limit ≤ upper_limit и что в успешной проверке есть не менее трех разных частот. Это правила целостности будущей БД. Сейчас диаграмма является проектом, подключения к PostgreSQL в программе нет.

## Автоматизируемые операции

`n` — число строк CSV, `c` — число полей строки, `s` — размер выходного JSON. Для текущего формата `c = 3`. При оценке считаем длину номера изделия и числовых значений ограниченной форматом.

| Операция | Вход | Результат | Время | Дополнительная память |
| --- | --- | --- | --- | --- |
| Проверка CSV | Заголовок и строки | Проверенные измерения или ошибка | O(n × c), при c = 3 это O(n) | O(n) для списка и множества частот |
| Поиск максимального отклика | Частоты и ускорения | Частота единственного внутреннего максимума | O(n) | O(n) в текущем коде из-за списков и множества |
| Проверка допуска | Частота, целевое значение и допуск | «Годен» или «Не годен» | O(1) | O(1) |
| Сохранение результата | Словарь результата | JSON | O(s) | O(s) как верхняя оценка сериализации |

Проверка повторов через множество имеет ожидаемое линейное время. Поиск максимума, его количества и границ выполняется несколькими проходами по спискам. Число проходов не растет с размером файла, поэтому итог остается O(n). Проверка допуска относится только к частоте, а не ко всему качеству изделия.

### Алгоритм 1

Внешний цикл обходит строки, внутренний — три обязательных поля строки. Затем проверяются числа. После чтения всех строк проверяются число точек, единый номер изделия и отсутствие повторных частот. Внутри алгоритма есть ветвления и вложенный цикл.

Это схема планируемой небольшой доработки `load_measurements`: сейчас поля проверяются отдельными выражениями. Явный внутренний цикл будет добавлен на следующем этапе реализации. Ошибка преобразования числа также завершает обработку с сообщением.

### Алгоритм 2

Сначала находится максимальное ускорение. Если максимум нулевой или повторяется, частоту не выбираем. Максимум на краю диапазона также дает ошибку: диапазон измерений нужно расширить. В остальных случаях частота сравнивается с границами допуска включительно.

При учебных настройках `target_hz = 170`, `tolerance = 10` годный диапазон — от 160 до 180 Гц. Частота выбирается из таблицы без интерполяции и не выдается за точное измерение механического резонанса.

### Обозначения блок-схем

Использованы символы ГОСТ 19.701–90: процесс — прямоугольник, данные — параллелограмм, решение — ромб, начало и конец — скругленный прямоугольник. Направление выполнения показывают стрелки, выходы решений подписаны. [Карточка стандарта Росстандарта](https://protect.gost.ru/gost/details/0c85e066-f89e-433d-a6d3-b7f746bd0c7c).

## Как посмотреть диаграммы

PNG можно открыть прямо в VS Code. Исходники `.puml` также можно открыть расширением PlantUML или обработать локальным PlantUML с Graphviz. Команда для среды, где они установлены:

```bash
java -jar plantuml.jar -tpng models/*.puml
```

`plantuml.jar` здесь означает путь к установленному PlantUML. Он не входит в проект и не нужен для запуска Python-программы. `process.bpmn` открывается в BPMN-редакторе. Используемая спецификация — [BPMN 2.0.2 от OMG](https://www.omg.org/spec/BPMN/2.0.2/).
