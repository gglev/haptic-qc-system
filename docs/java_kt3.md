# Java-версия программы

## Связь с КТ2

Основа сравнения — процедурная версия из коммита 4e5795f. В ней уже учтены повторные проверки одного изделия. В Java сохранены формат входа, формулы сглаживания, допуски, статусы и состав результата. Порядок записей в исходном JSON сохраняется в списке протоколов. Для расчета итогов по изделиям создается отдельный отсортированный список.

| Сущность ER-модели | Класс Java | Что хранит |
| --- | --- | --- |
| ProductModel | qc.model.ProductModel | Идентификатор и название модели |
| Lot | qc.model.Lot | Номер партии и ссылку на модель |
| Product | qc.model.Product | Серийный номер и ссылку на партию |
| Employee | qc.model.Employee | Идентификатор, логин и ФИО сотрудника |
| Recipe | qc.model.Recipe | Версию методики, модель, утвердившего сотрудника, дату и окно |
| Parameter | qc.model.Parameter | Код, название и единицу параметра |
| RecipeLimit | qc.model.RecipeLimit | Связь методики с параметром и границы допуска |
| TestRun | qc.model.TestRun | Изделие, методику, оператора, время, статус, точки и результат |
| Measurement | qc.model.Measurement | Номер точки, частоту и ускорение |

Составной ключ Measurement представлен номером точки внутри TestRun. Номера разных проверок могут совпадать. В RecipeLimit остаются ссылки на обе стороны связи M:N. Идентификаторы из файла используются загрузчиком для поиска объектов, затем связи между объектами задаются ссылками.

## Наследование, интерфейс и коллекции

Metrolog наследует Employee и меняет поведение canApproveRecipe. У обычного сотрудника метод возвращает false, у метролога — true. Recipe принимает ссылку Employee и вызывает этот метод при создании. Проверка кода подтверждает, что оператору нельзя утвердить методику.

Для сохранения JSON КТ2 роль метролога определяется загрузчиком по approved_by в методиках. Такой сотрудник создается как Metrolog. Этот механизм описывает роль в учебном процессе и не выполняет авторизацию пользователя.

ResponseAnalyzer объявляет методы getWindowSize и analyze. RawResponseAnalyzer работает при окне 1, MovingAverageAnalyzer — при большем нечетном окне. Обе реализации вызываются программой. JsonIO выбирает нужный анализатор по настройке и передает его в Recipe. Методика проверяет размер окна и выполняет расчет через интерфейс. Код Recipe не зависит от конкретного класса анализатора.

List хранит точки и проверки. Map используется для поиска записей по идентификаторам и подсчета статусов. Set выявляет повторы ключей и номеров точек. Поля закрыты; коллекции TestRun и Batch снаружи доступны как неизменяемые списки. Изменение статуса проверки выполняется методом analyze.

UML разделена на общую схему и подробные схемы трех пакетов. Все девять исходных сущностей представлены классами. На схеме данных показаны ассоциации с кратностью, наследование Employee — Metrolog и композиция TestRun — Measurement. У Batch и TestRun показана агрегация: проверки могут существовать независимо от объекта набора. В схеме расчетов показана реализация интерфейса двумя анализаторами.

## Сопоставление версий

| Часть программы | Python КТ2 | Java КТ3 | Изменение парадигмы | Особенности языка |
| --- | --- | --- | --- | --- |
| Хранение данных | Словари со строковыми ключами и списки | Объекты сущностей со ссылками, List, Map, Set | Данные и связанные операции размещены в классах | У полей и коллекций указаны типы |
| Проверка измерений | check_response | ResponseRules.checkResponse и конструктор Measurement | Часть ограничений проверяется при создании объекта | double, BigInteger, IllegalArgumentException |
| Оценка отклика | analyze_response | ResponseAnalyzer.analyze, RawResponseAnalyzer и MovingAverageAnalyzer | Методика использует общий интерфейс; расчет можно заменить другим объектом | implements, Override, List с типами элементов |
| Подсчет партии | summarize_batch | BatchSummary и toMap | Сводка представлена отдельным объектом с закрытыми счетчиками | Comparator, Instant, Map<String, Integer> |
| Сохранение протокола | save_protocol | JsonIO.saveProtocol | Работа с файлом собрана в отдельном классе | Gson и Files вместо json и os.replace |
| Алгоритм 1 | Вложенный цикл по окнам, затем поиск максимума | Тот же вложенный цикл и общий AnalysisResult.evaluate | Реализация выбирается через интерфейс | Циклы for с типами и методы коллекций |
| Алгоритм 2 | Сортировка проверок и проход по группам изделий | Та же сортировка и проход в BatchSummary | Состояние счетчиков скрыто в объекте | Сравнение времени через Instant; null вместо None |
| Ошибки | Исключения Python и код завершения 1 | Исключения Java и код завершения 1 | Границы ответственности загрузчика и классов стали явными | Чтение и запись используют IOException и try-with-resources |
| Добавление другого способа обработки | Потребуется новая функция и выбор в analyze_response или вызывающем коде | Можно добавить реализацию ResponseAnalyzer и ее выбор в загрузчике | Recipe продолжит вызывать метод интерфейса | Новый Java-класс хранится в отдельном файле |

Число рабочих модулей Python — 2, функций — 10. В main.py и analysis.py вместе 293 строки, включая пустые строки и комментарии. Проверки checks.py в это число не включены. В Java — 19 исходных файлов программы: 18 классов и 1 интерфейс, всего 942 строки с пустыми строками и комментариями. Тестовый класс Checks подсчитан отдельно. Файлов стало больше из-за выделения сущностей и операций в классы и размещения открытых классов Java в отдельных файлах.

В Python удобнее проследить общий расчет по двум модулям. В Java отдельно видны данные изделия, методика, расчет и сохранение. Изменение правила обработки можно оформить отдельным классом, а доступ к данным ограничить методами. При этом формулы алгоритмов не изменились: вложенный цикл остается вложенным циклом, а сводка по-прежнему требует сортировки. Статическая типизация и обработка IOException связаны с языком Java. Наследование, интерфейс и инкапсуляция связаны с выбором ООП.

## Проверка совпадения

Программа проверена на JDK 21.0.12.1. Проверки qc.Checks содержат 32 утверждения: два ожидаемых результата, два анализатора, поведение метролога, порядок точек и проверок, границы допуска, время, пустую партию и ошибки входа. Дополнительно tools/compare_versions.py сравнивает версии на 100 входных наборах, включая 60 наборов с фиксированным начальным значением генератора. Сравниваются полные JSON, коды завершения и сохранность старого результата при ошибке. Расхождений в этих проверках нет.

В исходном примере получены PASS на 170 Гц, FAIL на 190 Гц и REVIEW при неоднозначном максимуме. В примере повторного контроля получены четыре проверки трех изделий и один повтор. Общая доля PASS равна 50 %, доля PASS среди последних проверок изделий — 66.66666666666667 %. Значения совпадают с Python.

Сглаживание занимает O((n−w+1)·w+n) времени и O(n) памяти. Сводка k проверок занимает O(k log k) времени и O(k) памяти. Смена языка и парадигмы сама по себе не изменила эти оценки. Длина идентификаторов и строк времени считается ограниченной.
