# 6. АНАЛИТИЧЕСКИЙ РАЗДЕЛ

## 6.1 Модель бизнес-процесса

В работе рассматривается выходной контроль партии вибротактильных модулей LRA. Процесс начинается с задания на контроль. В конце для каждого изделия должен быть сохранен протокол, а по партии должна быть получена сводка. Основная схема приведена на рисунке А.1, проверка одного изделия показана подробнее на рисунке А.2. Используется нотация BPMN 2.0.2 [19].

В одном пуле выделены четыре дорожки. ОТК обозначает отдел технического контроля, ПО — программное обеспечение. Инженер-метролог отвечает за методику измерений. MES ведет учет производственных операций, ERP связывает партию с заказом. В этой модели MES и ERP объединены в одну дорожку производственного учета.

Обязанности участников:

ОТК считывает серийный номер, устанавливает изделие в оснастку и после контроля сортирует его по полученному статусу.

ПО проверяет данные, рассчитывает частоту максимального отклика, сравнивает ее с допуском и сохраняет протокол.

Метролог утверждает методику, границы допуска и размер окна сглаживания. Если стенд не готов или результат измерений нельзя использовать, он выясняет причину и разрешает повторный запуск.

MES/ERP выдает задание на партию, принимает протокол и подтверждает регистрацию результата. При повторной отправке тот же идентификатор протокола не должен создавать новую запись.

Сначала проверяется готовность стенда. Затем выполняются измерение, проверка данных и расчет. Если данные неверные или максимум неоднозначен, процесс возвращается к метрологу. При выходе за допуск ОТК фиксирует несоответствие. При ошибке записи настроек ПО блокирует выпуск. После сохранения протокола ПО передает его в MES и ожидает подтверждение. Без подтверждения изделие не выпускается. В модели принят повтор отправки через 30 секунд; это условие работы системы, а не измеренная длительность контроля.

После обработки последнего изделия ПО подсчитывает результаты партии. На основной схеме показан свернутый подпроцесс контроля изделия, который раскрывается на второй схеме. Это позволяет читать основной процесс без большого числа мелких блоков.

Объекты данных на BPMN связаны с ER-моделью: «Методика и допуски» — Recipe, Parameter и RecipeLimit; «Модель, партия, изделия» — ProductModel, Lot и Product; «Точки измерений» — Measurement; «Протокол изделия» — TestRun. Сотрудники представлены сущностью Employee.

Таблица автоматизируемых операций находится под рисунком А.1. В ней названия задач связаны с функциями программы. В КТ2 реализована обработка уже подготовленных измерений. Управление стендом, запись в EEPROM и обмен с MES/ERP пока описаны только в модели процесса.

## 6.2 Логическая модель данных

На рисунке А.3 показаны девять сущностей в нотации Crow's Foot. PK означает первичный ключ, FK — внешний ключ, UQ — уникальное значение. Два штриха на конце связи обозначают ровно одну запись, окружность с «лапкой» — от нуля до многих записей, штрих с «лапкой» — от одной до многих. Типы SQL и индексы на этом этапе не задаются.

| Сущность | Назначение | Атрибуты | PK | FK |
| --- | --- | --- | --- | --- |
| Модель изделия / ProductModel | Название модели модуля | model_id, name | model_id | Нет |
| Партия / Lot | Партия изделий одной модели | lot_id, model_id, lot_number | lot_id | model_id → ProductModel |
| Изделие / Product | Отдельный модуль с серийным номером | product_id, lot_id, serial_number | product_id | lot_id → Lot |
| Сотрудник / Employee | Оператор ОТК или метролог | employee_id, login, full_name | employee_id | Нет |
| Версия методики / Recipe | Утвержденные условия обработки | recipe_id, model_id, version, approved_by, approved_at, window_size | recipe_id | model_id → ProductModel; approved_by → Employee |
| Параметр / Parameter | Величина, для которой задается допуск | parameter_id, code, name, unit | parameter_id | Нет |
| Допуск параметра / RecipeLimit | Границы для параметра в версии методики | recipe_id, parameter_id, lower_limit, upper_limit | recipe_id + parameter_id | recipe_id → Recipe; parameter_id → Parameter |
| Проверка изделия / TestRun | Один проход контроля изделия | run_id, product_id, recipe_id, operator_id, started_at, status | run_id | product_id → Product; recipe_id → Recipe; operator_id → Employee |
| Точка измерения / Measurement | Частота и ускорение в одной точке | run_id, point_no, frequency_hz, acceleration_m_s2 | run_id + point_no | run_id → TestRun |

Модель изделия может иметь несколько партий и версий методики. Каждая партия и каждая версия методики относятся к одной модели. В партии находятся изделия, у каждого изделия свой серийный номер. Одно изделие можно проверять несколько раз; для каждой проверки создается новый run_id.

Каждая проверка связана с одним изделием, одной версией методики и одним оператором. Один сотрудник может проводить несколько проверок и утверждать несколько методик. У каждой утвержденной версии методики указан один ответственный сотрудник.

Проверка может существовать без измерений до начала работы. Для расчета нужны хотя бы window_size + 2 точки. Номера точек и частоты внутри одной проверки не повторяются. Точки идут в порядке point_no, частоты возрастают с одинаковым шагом. Повторный проход оформляется новой проверкой.

У версии методики есть хотя бы один допуск. Один параметр может проверяться по разным методикам, а одна методика может включать несколько параметров. Поэтому связь «Методика — Параметр» является связью многие-ко-многим. Она раскрыта через RecipeLimit. Ключ этой сущности состоит из recipe_id и parameter_id. Границы допуска зависят от обоих значений. Пара model_id и version уникальна. После утверждения методика не редактируется; изменения оформляются новой версией.

Первая нормальная форма (1НФ). В каждом поле находится одно значение. Точки измерений хранятся отдельными записями, а не списком в записи проверки. JSON используется для передачи наборов записей и не является одним полем таблицы.

Вторая нормальная форма (2НФ). Неключевые поля зависят от всего ключа. В RecipeLimit границы допуска задаются для пары «версия методики — параметр». В Measurement частота и ускорение относятся к паре «проверка — номер точки».

Третья нормальная форма (3НФ). Данные о сотруднике, модели и параметре хранятся в своих сущностях [21]. Например, ФИО оператора не записывается заново в каждую проверку. Если фамилия изменится, достаточно исправить одну запись Employee. Проверки останутся связаны с ней через operator_id. Так устраняется дублирование и риск разных ФИО у одного сотрудника.

Частота максимума и проценты по партии рассчитываются программой. В исходных сущностях ER-модели они повторно не хранятся.

## 6.3 Алгоритмы

Для КТ2 выбраны два алгоритма: оценка частотного отклика и подсчет результатов партии. На блок-схемах используются обозначения ГОСТ 19.701-90 [20]: ввод и вывод — параллелограмм, условие — ромб, цикл — шестиугольник. Ветви условий подписаны «Да» и «Нет». Схемы показывают расчет после проверки входа функциями load_batch и check_response.

### Алгоритм 1 Оценка частотного отклика

Задача BPMN: «Оценить частотный отклик». Функция: analyze_response. Блок-схема приведена на рисунке А.4.

Входные данные: точки Measurement одной проверки, размер окна window_size из Recipe, нижняя и верхняя границы из RecipeLimit. Число точек обозначено n, ширина окна — w. Окно положительное и нечетное, сетка частот равномерная и возрастающая. После сглаживания должны остаться хотя бы три точки.

Выходные данные: статус PASS, FAIL или REVIEW, частота максимума и пояснение reason. При REVIEW частота не определяется и в JSON записывается null.

Порядок выполнения:

1. Для каждого полного окна сложить w значений ускорения и разделить сумму на w. Полученное среднее отнести к частоте центральной точки окна.

2. Найти наибольшее среднее значение и собрать все точки, близкие к нему. Для сравнения используется math.isclose с rel_tol=10^-9 и abs_tol=10^-12. Это параметры сравнения чисел, а не оценка погрешности измерений.

3. Если максимум неположительный или найдено несколько максимумов, вернуть REVIEW: по этим данным нельзя выбрать одну частоту.

4. Если максимум находится на краю сглаженной характеристики, вернуть REVIEW с предложением расширить диапазон измерений.

5. В остальных случаях сравнить частоту максимума с допуском. Если нижняя граница <= частота <= верхняя граница, вернуть PASS. Иначе вернуть FAIL.

Пример сглаживания: для частот 160, 170 и 180 Гц и ускорений 3, 8 и 3 м/с² среднее равно 14/3 м/с². Оно относится к центральной частоте 170 Гц. Неполные окна не используются. Частота выбирается из исходной сетки без интерполяции. Это обработка частотной характеристики, а не спектральный анализ временного сигнала.

Внешний цикл выполняет n - w + 1 проходов. На каждом проходе внутренний цикл складывает w чисел. Поиск максимума и равных ему значений требует еще O(n) операций. Время расчета составляет O((n - w + 1) * w + n), верхняя граница — O(n * w) [22].

Если w растет вместе с n и имеет порядок n/2, худший случай по n составляет O(n²). При постоянном окне w = 3, как в примере, время равно O(n). Память составляет O(n) для сглаженных точек и списка максимумов. В программе суммы окон рассчитываются заново; обновление суммы при сдвиге окна не используется.

Размер окна утверждает метролог. При w = 1 сглаживания нет. Перед работой на реальном стенде нужно проверить, не смещает ли выбранное окно максимум. Учебный пример этого не подтверждает. Все точки одного прохода должны быть получены при одинаковом возбуждении и креплении изделия.

### Алгоритм 2 Подсчет результатов партии

Задача BPMN: «Подсчитать результаты партии». Функция: summarize_batch. Блок-схема приведена на рисунке А.5.

Входные данные: k результатов проверок со статусами PASS, FAIL или REVIEW.

Выходные данные: общее число проверок, число каждого статуса и доля PASS в процентах.

Порядок выполнения:

1. Присвоить счетчикам passed, failed и review значение 0.

2. Просмотреть каждый результат один раз. Увеличить счетчик, который соответствует его статусу.

3. Сложить три счетчика и получить total.

4. Если total равен 0, вернуть pass_percent = null. Иначе вычислить pass_percent = 100 * passed / total.

5. Вернуть счетчики, общее число проверок и процент PASS.

Цикл выполняется k раз. На каждом проходе выполняется постоянное число сравнений и одно увеличение счетчика. Поэтому время в худшем случае равно O(k), дополнительная память — O(1). Входной список в дополнительную память не включается. Повторные проверки одного изделия считаются отдельно: сводка показывает результаты проверок, а не долю брака среди уникальных изделий.

Оценки двух алгоритмов при переменной ширине окна различаются: O(n²) и O(k). У всей программы есть и затраты на подготовку данных: точки каждой проверки сортируются по point_no за O(n log n) в худшем случае. Для k проверок по n точек сортировка дает O(k * n log n), а расчет отклика — O(k * ((n - w + 1) * w + n)). Проверки ссылок используют словари и множества, для которых обычно принимается среднее постоянное время доступа.

## 6.4 Процедурная реализация

Программа написана на Python с синтаксисом версии 3.11 [15]. Используются функции, списки и словари. Пользовательских классов и глобальных изменяемых данных нет. Внешние библиотеки не требуются.

| Функция | Что получает | Что делает или возвращает |
| --- | --- | --- |
| load_batch | Путь к входному JSON | Проверяет файл и связи. Возвращает данные для расчета. |
| check_response | Точки и размер окна | Проверяет числа, сетку частот и размер окна. |
| analyze_response | Точки, окно, допуск | Возвращает статус, частоту и причину решения. |
| summarize_batch | Результаты проверок | Считает статусы и долю PASS. |
| save_protocol | Готовый результат и путь файла | Сохраняет протокол в JSON. |

Входной JSON содержит девять списков, соответствующих сущностям ER-модели. Связи задаются идентификаторами. Статус NEW означает, что проверка еще не обработана. Методика должна подходить модели изделия, а один входной файл должен содержать проверки одной партии. Все входные данные проверяются до расчета.

В протокол записываются run_id, product_id, serial_number, recipe_id, границы допуска, частота максимума, status и reason. В сводке находятся total, passed, failed, review и pass_percent. Это результат обработки, а не новая исходная таблица ER-модели.

Для проверки подготовлен учебный файл src/examples/batch.json. Его значения заданы заранее и не являются измерениями стенда.

| Изделие | Частота, Гц | Статус | Причина |
| --- | --- | --- | --- |
| DEMO-001 | 170 | PASS | Частота входит в допуск 160–180 Гц. |
| DEMO-002 | 190 | FAIL | Частота выше верхней границы. |
| DEMO-003 | Не определена | REVIEW | Плоская характеристика: нет одного максимума. |

Итог примера: три проверки, по одной каждого статуса. Доля PASS равна 33,33 %. PASS означает, что выполнен только допуск частоты максимального отклика. Для полного заключения о годности модуля нужны и другие проверки.

Запуск из корня проекта:

python3 src/main.py

Для своего файла:

python3 src/main.py src/examples/batch.json result.json

Запуск проверок:

python3 src/checks.py

Инструкция находится в src/README.md. Успешная обработка завершается с кодом 0 даже при FAIL или REVIEW. Ошибка чтения, входных данных или сохранения дает код 1. Если вход неверный, обработка партии прекращается до записи нового результата.

Протокол сначала полностью записывается во временный файл в той же папке. Только после успешной записи он заменяет предыдущий результат. Если возникла ошибка, старый файл сохраняется и относится к прошлому запуску. Поэтому нужно смотреть сообщение программы и код завершения.

В checks.py проверяются расчет частоты, обе границы допуска, выход за допуск, окно 1, плато, нулевой сигнал и максимум на краю. Также проверяются неверная сетка частот, недостаток точек, отрицательные и нечисловые значения, пустая партия, потерянные ссылки и повтор ключа. Отдельные проверки подтверждают, что порядок записей во входном JSON не меняет результат, ошибочный запуск не заменяет старый протокол, а выходной файл не совпадает с входным.

Программа и проверки запускались на установленном Python 3.14.7. Совместимость синтаксиса проверена для 3.11; запуск на самом Python 3.11 пока не проверен.

В КТ2 обрабатываются готовые измерения из файла. Управление стендом, оценка неопределенности измерений, запись EEPROM, PostgreSQL и обмен с MES/ERP еще не реализованы. В КТ3 расчет будет перенесен на Java с использованием классов, в КТ4 будет подготовлена физическая модель данных.
